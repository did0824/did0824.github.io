사내 컴포넌트 라이브러리

Internal component library

여섯 개 서비스가 각자 React Three Fiber 기반 위성 시각화 UI를 따로 구현하고 있었습니다. 같은 기능이 서비스마다 다르게 동작했고, 한 곳에서 고친 내용이 다른 곳으로 넘어가지 않았습니다. 버그 하나를 여섯 번 고치는 상황이었습니다.

Six services each had their own React Three Fiber satellite visualization UI. The same feature behaved differently in every one of them, and a fix in one place never reached the others. Every bug had to be fixed six times.

어디까지 열어줄 것인가

How much to open up

반복되는 시각화 UI를 React 컴포넌트로 묶어 digital-twin-package로 만들었습니다. 이때 가장 오래 고민한 건 컴포넌트 목록이 아니라 인터페이스의 폭이었습니다.

I pulled the recurring visualization UI into React components and shipped it as digital-twin-package. What took longest to settle was not the list of components but how wide the interface should be.

three.js 인스턴스나 렌더 루프를 밖으로 노출하면 당장은 편합니다. 쓰는 쪽이 뭐든 할 수 있으니까요. 하지만 그 순간 내부 구현이 곧 공개 API가 되어, 안쪽을 고칠 때마다 여섯 개 서비스가 깨집니다. 그래서 props만으로 제어하는 선언적 인터페이스로 좁혔습니다. 쓰는 쪽은 3D 렌더링 내부를 몰라도 되고, 저는 안쪽을 자유롭게 바꿀 수 있습니다.

Exposing the three.js instance or the render loop is the easy path — consumers can then do anything. But at that moment the internals become the public API, and every change inside breaks six services. So I narrowed it to a declarative interface driven by props alone. Consumers never need to know the 3D rendering internals, and I stay free to change them.

// 쓰는 쪽이 보는 전부. 워커도, 렌더 루프도, 버퍼도 보이지 않습니다.

  <TleRso
    rsoData={{ name: 'starlink', data: tles, color: '#4cc9f0', orbit: true }}
    handleRsoClick={(sat) => select(sat)}
  />
  <RsoTag groupName="starlink" noradId={44713} position="best" tail>
    STARLINK-1007
  </RsoTag>
</Scene>
// Everything the consumer sees. No workers, no render loop, no buffers.

틀린 조합은 컴파일에서 막습니다

Wrong combinations fail at compile time

센서의 시야각 컴포넌트가 좋은 예입니다. 원뿔이면 대각 화각 하나를, 사각뿔이면 수평·수직 화각 두 개를 받습니다. 섞어 쓰면 의미가 없는데, 이걸 런타임 경고로 처리하면 쓰는 사람은 화면이 이상해진 뒤에야 알게 됩니다.

The sensor field-of-view component is a good example. A cone takes one diagonal angle; a rectangular pyramid takes a horizontal and a vertical one. Mixing them is meaningless, and if that is only a runtime warning the consumer finds out after the screen already looks wrong.

// 둘 중 하나만. 섞으면 타입 에러.
<Cone dfov={30} />                // 원뿔
<Cone hfov={20} vfov={10} />      // 사각뿔
<Cone dfov={30} hfov={20} />      // ✗ 컴파일 실패
// One or the other. Mixing is a type error.
<Cone dfov={30} />                // cone
<Cone hfov={20} vfov={10} />      // rectangular pyramid
<Cone dfov={30} hfov={20} />      // ✗ compile error

각도 단위도 전체 각으로 통일하고 유효 범위 밖은 잘라냅니다. 문서에 “주의하세요”라고 적는 대신 타입으로 막는 편이 낫습니다. 문서는 안 읽히지만 컴파일러는 항상 돕니다.

Angle units are normalized to full angles and out-of-range values are clamped. Better to block it in the type system than to write “be careful” in the docs. Docs go unread; the compiler always runs.

모노레포를 쓰지 않기로 했습니다

We decided against a monorepo

패키지가 늘어나면 모노레포를 떠올리는 게 자연스럽지만 도입하지 않았습니다. 서비스마다 릴리스 주기가 독립적이었고, 소비하는 쪽 중에는 폐쇄망에 반입되는 제품도 있어 배포 경로 자체가 달랐기 때문입니다. 통합 빌드로 얻는 이점보다는 각자 버전을 고정해둔 채 필요할 때 올릴 수 있는 편이 이 조직에 맞았습니다. 대신 배포는 자동화해서, git 태그를 밀면 GitHub Actions가 번들하고 버전을 붙여 퍼블리시합니다.

A monorepo is the natural thought once packages pile up, but we did not adopt one. Release cycles were independent per service, and some consumers shipped into air-gapped networks, so the delivery paths themselves differed. Pinning a version and bumping it when ready suited this organization better than what a unified build would have bought us. Releases are automated instead: push a git tag and GitHub Actions bundles it, stamps the version and publishes.

설치 한 번으로 끝나게 만들기

Making installation the only step

이 패키지는 WASM 커널과 전용 워커를 함께 씁니다. 평범하게 번들하면 쓰는 쪽이 wasm 바이너리와 glue 스크립트를 직접 서빙해야 합니다. 라이브러리 하나 쓰자고 배포 설정을 건드리게 되는 거죠.

This package ships a WASM kernel alongside a dedicated worker. Bundled the ordinary way, consumers would have to serve the wasm binary and glue script themselves — touching their deployment setup just to use one library.

번들러 플러그인을 직접 만들었습니다. 빌드 시점에 워커 소스와 glue, wasm 바이너리를 하나로 합치고, 워커 생성 호출을 Blob 기반으로 치환합니다.

So I wrote a bundler plugin. At build time it merges the worker source, the glue and the wasm binary into one file, and rewrites worker construction to a Blob.

아홉 번의 메이저 버전

Nine major versions

지금 v9까지 왔습니다. 소비자가 여섯이면 깨지는 변경을 낼 때 "바뀌었습니다"만으로는 부족합니다. 시야각 볼륨의 거리 기준을 축 방향 높이에서 시선 거리로 바꿨을 때는, 기존 크기를 유지하려면 어떤 값을 넘겨야 하는지 계산식과 함께 공지했습니다.

We are at v9 now. With six consumers, “this changed” is not enough when you ship a breaking change. When the field-of-view volume switched its distance basis from axial height to slant range, the announcement carried the formula for what value to pass to keep the existing size.

실시간 렌더링 재설계

Real-time rendering redesign

위성 궤도 전파(SGP4)를 메인 스레드에서 돌리고 있었습니다. 객체가 늘자 프레임이 끊기기 시작했고, 조금 더 올리면 화면 조작 자체가 먹지 않았습니다. 계산과 렌더링과 사용자 입력이 한 줄에 서 있었으니까요.

Satellite orbit propagation (SGP4) was running on the main thread. As the object count grew the frame rate began to stutter, and a little higher the camera stopped responding at all — computation, rendering and user input were all standing in one line.

먼저 계측기를 만들었습니다

The instrument came first

어디가 느린지는 짐작으로 알 수 없어서 성능 측정 오버레이를 먼저 만들었습니다. 프레임 시간과 구간별 비용을 화면에 띄워두고 보는 도구인데, 위에 있는 데모의 숫자판이 그때 만든 것과 성격이 같습니다. 이후 결정은 전부 이 숫자를 보고 내렸습니다.

There was no guessing where the time went, so a performance overlay came first. It keeps frame time and per-stage cost on screen; the readout in the demo above is the same kind of tool. Every decision after that came from those numbers.

계산을 옮기고, 주기를 끊었습니다

Moving the work off, breaking the cadence

SGP4 커널만 네이티브 라이브러리를 WebAssembly로 컴파일해 여러 Web Worker에 나눠 넣었습니다. 워커도 역할을 나눴습니다. 본체 전파를 분담하는 워커들과 별개로, 궤도선 샘플링만 맡는 워커를 따로 뒀습니다. 궤도선 계산이 길어져도 본체 갱신이 막히지 않게요. 여기서 한 걸음 더 갔습니다. 워커가 좌표만 돌려주면 메인 스레드가 다시 행렬을 만들어야 하니, 4×4 변환행렬까지 워커에서 만들어 SharedArrayBuffer에 직접 씁니다. 메인 스레드는 복사 없이 읽기만 합니다.

Only the SGP4 kernel was compiled from the native library to WebAssembly and split across several Web Workers. The workers were split by role as well: apart from those sharing body propagation, one worker handles orbit-line sampling and nothing else, so a long orbit-line pass never blocks body updates. Then one step further. If a worker returns only coordinates the main thread has to rebuild the matrices, so the workers build the 4×4 transforms too and write them straight into a SharedArrayBuffer. The main thread only reads, with no copy.

그다음은 주기 분리였습니다. 궤도를 초당 60번 다시 계산할 이유는 없으니, 워커 틱 사이를 케플러 전개로 보간해 계산 주기와 렌더 주기를 떼어놨습니다. 계산을 덜 해도 화면은 부드럽습니다.

Next came decoupling the cadence. There is no reason to recompute an orbit sixty times a second, so Kepler propagation interpolates between worker ticks and the compute rate is separated from the render rate. Less computation, and the screen still moves smoothly.

보간을 얼마나 멀리까지 허용할지는 오차를 계산해서 정했습니다. 100초 앞은 약 1미터, 300초 앞은 약 4km, 600초 앞은 80km까지 벌어집니다. 그래서 300초를 상한으로 잡았습니다. 상한을 넘을 때 보간을 0으로 되돌리면 점이 궤도를 따라 뒤로 튀는 게 한 프레임 보여서, 값을 고정하는 쪽을 택했습니다. 눈에 보이는 것과 수치상 정확한 것이 다를 때가 있습니다.

How far to let the interpolation run came out of an error budget. A hundred seconds ahead drifts about a meter, three hundred about 4 km, six hundred as much as 80 km. So 300 seconds became the ceiling. Snapping the interpolation back to zero past that ceiling showed a one-frame jump backwards along the orbit, so I chose to hold the value instead. What looks right and what is numerically right are not always the same thing.

고칠 수 없는 라이브러리를 우회하기

Working around a library I could not fix

번들된 네이티브 라이브러리에는 등록한 위성을 제거하는 함수가 있습니다. 그런데 이 함수가 내부 배열을 재정렬하면서 아직 살아 있는 다른 핸들을 무효화합니다. 이후 초기화 루틴이 그 핸들을 역참조하다 메모리 접근 오류로 죽습니다. 3만 기 이상을 고속 재생할 때 재현됐습니다.

The bundled native library has a function for removing a registered satellite. It reorders an internal array as it goes, invalidating other handles that are still live. A later initialization routine dereferences one of them and dies on a memory access fault. It reproduced while scrubbing at speed through 30,000 objects and up.

핸들이 계속 쌓이는 이유가 있었습니다. 같은 TLE는 같은 핸들을 재사용하도록 캐시해두는데, 고속 재생 중에는 TLE의 기준 시각이 바뀌면서 위성 하나가 수백 개의 핸들을 만들어냅니다.

There was a reason the handles kept piling up. Identical TLEs are cached so they reuse one handle, but during fast playback the TLE epoch shifts, so a single satellite produces hundreds of them.

라이브러리를 고칠 수는 없었습니다. 그래서 제거 함수를 아예 호출하지 않기로 하고, 대신 워커 자체를 교체해 메모리를 회수했습니다. 캐시가 한계를 넘으면 워커가 신호를 보내고, 메인 스레드가 그 워커만 종료한 뒤 새로 띄워 담당 구간을 다시 등록합니다. 워커를 끝내면 그 안의 WASM 인스턴스가 통째로 사라지므로, 개별 해제 없이도 메모리가 돌아옵니다. 교체하는 동안에는 그 워커에 작업을 보내지 않습니다. 종료된 워커는 완료 신호를 올릴 수 없어서, 그대로 두면 나머지 워커가 영원히 기다리게 됩니다.

I could not fix the library. So I stopped calling the removal function at all and reclaimed the memory by replacing the worker itself. When a cache crosses its limit the worker signals, the main thread terminates that one worker, starts a fresh one and re-registers its slice. Ending a worker takes the whole WASM instance with it, so the memory comes back without freeing anything individually. No work is dispatched to that worker while it is being replaced: a terminated worker can never report completion, and left in the rotation it would make the others wait forever.

나머지는 세부 작업이었습니다. InstancedMesh로 드로우콜을 줄이고, 라벨 갱신은 30Hz에서 15Hz로 내렸습니다. 라벨 겹침 판정이 매 프레임 레이아웃을 건드리고 있어서 공유 rAF와 DOM diff 캐시, 공간 해시로 다시 짰습니다. 버퍼 인덱스 할당자를 따로 두고, 저사양 GPU에서는 품질을 자동으로 낮춥니다.

The rest was detail work. InstancedMesh cut draw calls, and label refresh dropped from 30Hz to 15Hz. Label overlap testing was touching layout every frame, so it was rewritten around a shared rAF, a DOM diff cache and a spatial hash. A separate buffer index allocator went in, and quality steps down automatically on low-end GPUs.

CPU 사용량이 약 20% 줄었습니다. 더 중요한 건 객체가 늘어도 조작이 막히지 않게 된 것이었습니다.

CPU usage dropped by about 20%. What mattered more was that interaction stopped locking up as the object count grew.

LLM 기반 플랫폼 제어 — 설계 완료, 도입 진행 중

LLM-driven platform control — designed, rollout in progress

궤도역학은 어렵습니다. 제품에 기능은 다 있는데, 사용자가 메뉴에서 그걸 찾지 못했습니다. UI를 더 잘 정리하는 방법도 있었지만, 도메인 자체의 난이도는 정리로 해결되지 않습니다. 그래서 자연어로 플랫폼을 조작하는 층을 설계했습니다.

Orbital mechanics is hard. The product had every feature, and users still could not find them in the menus. Reorganizing the UI was one option, but tidying does not reduce the difficulty of the domain itself. So I designed a layer that drives the platform in natural language.

서버는 자동으로, 클라이언트는 손으로

Automatic on the server, by hand on the client

백엔드는 기존 API를 자동으로 툴로 노출합니다. 이미 스키마라는 계약이 있으니 툴 정의를 따로 관리할 이유가 없고, API가 늘어도 손댈 곳이 생기지 않습니다.

The backend exposes its existing APIs as tools automatically. The schema is already a contract, so there is no reason to maintain tool definitions separately, and new APIs add nothing to touch.

프론트엔드는 그렇게 할 수 없었습니다. 클라이언트 상태에는 계약이 없습니다. three.js 씬이나 필터 상태를 그대로 열면 내부 구현이 다시 외부 인터페이스가 되고, 리팩터링할 때마다 깨집니다. 그래서 LLM이 호출할 규약을 프론트엔드에 미리 정의했습니다. 조회만이 아니라 화면 상태 변경까지 이 규약을 거칩니다. LLM은 상태를 직접 만지지 않고, 정해진 전이만 호출합니다.

The frontend could not work that way. Client state has no contract. Opening up the three.js scene or the filter state would turn internals into an external interface again, breaking on every refactor. So I defined the protocol the LLM is allowed to call, up front, in the frontend. Not just reads — screen state changes go through it too. The LLM never touches state directly; it calls defined transitions.

규약을 세우려면 경로가 하나여야 했습니다

A protocol needs a single path

여기서 예상하지 못한 일이 생겼습니다. 규약이 성립하려면 상태가 바뀔 때 데이터와 화면이 같은 경로로 따라온다는 보장이 있어야 합니다. 그런데 화면마다 데이터를 가져오는 방식과 그리는 방식이 제각각이었습니다. 그 상태로는 규약을 정의할 수가 없었습니다.

Something unexpected came up here. For the protocol to hold, data and screen have to follow the same path whenever state changes. But every screen fetched and drew its data its own way. There was no defining a protocol on top of that.

그래서 데이터 파이프라인과 렌더링 경로를 하나로 통합했습니다. AI 기능을 붙이려던 일이 프론트엔드 구조를 정리하는 일이 된 셈입니다.

So the data pipeline and the rendering path were unified. What began as attaching an AI feature turned into straightening out the structure of the frontend.

결과적으로 툴 표면이 둘로 갈렸습니다. 양쪽의 변경 비용과 안전성 요구가 다르기 때문입니다. 컴포넌트의 props를 좁힐 때와 같은 판단이었습니다. 안쪽을 감추고 경계만 연다는 것.

The tool surface ended up split in two, because the two sides differ in cost of change and in what they need to keep safe. It was the same judgment as narrowing a component’s props. Hide the inside, open only the boundary.
